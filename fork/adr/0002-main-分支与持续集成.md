# 0002. main、upstream 分支与 Fork CI

- **日期：** 2026-08-31
- **Fork-ADR：** 0002

## Context

上游合入闸门是 `.github/workflows/blocking-ci.yml` 的 `CI required`，下面挂 Bazel、自托管 Windows、BuildBuddy、`macos-15-xlarge`。仓库名同样是 `codex` 时，表达式 `github.event.repository.name-runners` 会去找并不存在的 `codex-runners`，检查会一直排队。`v8-canary.yml` 在 PR 上也会自己跑。

[WAcry/codex](https://github.com/WAcry/codex) 调查时：main 无 branch protection / ruleset；三种 merge 都开着；Actions 总开关是开的，但 workflow 列表为空；没有自托管 runner。

我们要在 GitHub 上编、测、发，同时不改那 20 多份上游 YAML（改了每次同步都冲突）。上游开发主线还要持续可见，但 fork 的 `main` 不能提前带入尚未发布的代码。功能改动必须走 PR；发布基线同步也要先用临时 PR 跑完 CI。

## Decision

### 分支

- `origin/upstream` 镜像 `openai/codex` 的 `main`，只放上游原始历史，不放 fork commit。
- `origin/main` 的提交历史由“最新采用的上游 `rust-v*` 发布标签 + rebased fork commits”组成。alpha / beta 标签也算发布；普通的上游 `main` commit 不进 fork `main`。
- `.github/workflows/fork-sync-upstream.yml` 每天 fast-forward 一次 `origin/upstream`，也可手动触发。上游若改写 `main` 导致不能 fast-forward，workflow 直接失败，不自动 force push。

上游出了要采用的新版本后，从当前 `origin/main` 建立临时 `sync/...` 分支，以旧 release tag 为边界，把 fork commits rebase 到新 release tag。解决冲突时只重新应用 `OVERLAY.md` 中的补丁，不 merge `origin/upstream`。`origin/upstream` 用于观察开发主线和发现新 Release，不是发布基线。

同步分支开 PR 只做审查和 CI。`fork-ci.yml` 明确 checkout PR head，不测试 GitHub 生成的临时 merge commit。`Fork CI` 全绿后，临时停用 `main` ruleset，用 `--force-with-lease` 把 `main` 更新到该分支，再立即恢复 ruleset并关闭、删除临时分支。不要点击 GitHub 的 merge：同步分支与旧 `main` 历史分叉，三方合并会把旧基线独有的代码重新带回来。

### 工作流文件

新增三份，只服务本 fork：

- `.github/workflows/fork-ci.yml`：PR 检查与合并后的 `main` 完整 fork 测试集
- `.github/workflows/fork-release.yml`：见 ADR 0001
- `.github/workflows/fork-sync-upstream.yml`：更新上游开发主线镜像

三份都加 `if: github.repository == 'WAcry/codex'`，避免再 fork 出去时误跑。

不修改上游任何已有的 `.github/workflows/*.yml`。它们进到 Actions 列表之后，用 `fork/scripts/disable-upstream-workflows.ps1` 全部禁用，只留上面三份。`v8-canary`、`rust-release`、`blocking-ci`、`postmerge-ci` 都在禁用名单里。

### 验证阶段

本 fork 通常只做最小补丁，PR 优先保持验证反馈快。完整 fork 测试集集中到合并后的 `main`，本地只做格式与静态检查。GitHub-hosted only。Release commit 的 workspace 版本是真实版本，而上游锁文件和 TUI snapshots 仍使用 `0.0.0`；CI 在临时 checkout 中先恢复 `0.0.0`。

- PR 的 Linux `ubuntu-24.04`：`cargo fmt --check`（与上游 rust-ci 相同的 `imports_granularity=Item`）、`cargo clippy --locked --bin codex`、`cargo check --locked --release --bin codex`
- Windows `windows-latest`：`cargo check --locked --release --bin codex`
- 合并后的 `main`：执行上述检查，再在 Linux 用 `just test` 跑 `codex-core` 的 lib 测试、`codex-cli` 的 `codex` binary tests、`codex-tui` 的 crate 测试，以及 [ADR 0004](0004-fork-历史-item-ID.md) 指定的 fork 历史集成回归测试。`push main` 自动触发；手动运行时选择 `main` 才执行测试。

两边都走 `.github/actions/setup-ci` 和对应 target 的 `setup-rusty-v8`。聚合 job 名称固定为 `Fork CI`，这是 ruleset 里唯一的 required check。

release check 不能删：`tui/src/updates.rs` 等模块在 debug 构建中根本不编译。不做 Bazel、不做 `rust-ci-full`、不把 `sdk.yml` 当 required。

### 合并规则

普通功能改动只能通过 PR 更新 `main`。允许的合并方式只有 squash。合并后删头部分支。禁止删除 `main`，日常禁止 force push。要求普通 PR 分支相对 `main` 是最新。required 检查：`Fork CI`。`bypass_actors` 为空。

PR 批准人数为 0，一个人也可以在 CI 绿了之后 squash。CODEOWNERS 不当作强制评审（上游 team 在本 fork 不存在）。

main 只保留这里明确写出的 PR 和 `Fork CI` 门禁。不要再叠加审批人数、标签保护、环境保护或重复检查。默认维护者遵守发布和同步约定。

发布基线同步是 force push 的唯一例外，而且必须先让对应临时 PR 的 `Fork CI` 通过。具体命令见 `fork/README.md`。

功能改动：独立分支，commit 带 `Fork-ADR: NNNN`，squash 进 `main`。

### GitHub 仓库开关

- `allow_squash_merge=true`
- `allow_merge_commit=false`
- `allow_rebase_merge=false`
- `delete_branch_on_merge=true`

用 repository ruleset 实现分支保护，不要用已废弃的 classic branch protection（当前 main 上也没有 classic 规则）。

GitHub 上的 ruleset 和 merge 开关不在 git 里，丢了按本 ADR 的 Decision 重建。

## Coupling

上游改 `setup-ci`、`setup-rusty-v8`、`codex-rs` 的 fmt 配置、或把 `codex` 二进制挪出 `codex-cli`，fork-ci 会红。禁用名单依赖 workflow 的文件名；上游新增 yml 时要再跑一次 disable 脚本。同步 workflow 依赖 `origin/upstream` 已存在且只能 fast-forward。

Ruleset 写死检查名 `Fork CI`。改 job 的 `name:` 会让 main 合不进去，直到 ruleset 一起改。

## Reapply

fork 的三个 workflow 被同步冲掉：按本 ADR 加回文件，确认 CI 聚合 job 仍叫 `Fork CI`。

上游新加了会自动跑的 workflow：跑 `fork/scripts/disable-upstream-workflows.ps1`。不要在上游 yml 里加 `if: github.repository == 'openai/codex'` 来“顺手修”，那是大面积补丁。

Ruleset 被删：用 GitHub API 按 Decision 重建，`bypass_actors` 保持空。

## 如何确认

```text
gh api repos/WAcry/codex --jq "{allow_squash_merge,allow_merge_commit,allow_rebase_merge,delete_branch_on_merge}"
# 期望：squash true，另外两个 merge false，delete_branch_on_merge true

gh api repos/WAcry/codex/rulesets
# main ruleset：required check 为 Fork CI，分支必须最新，bypass 为空

git ls-remote origin refs/heads/upstream
# SHA 应等于 openai/codex main；fork-sync-upstream 每天更新它

# 普通 PR：应出现 Fork CI，绿了才能 squash 进 main。
# PR：只运行格式、Clippy 和编译检查。
# 合并后：main 的 Linux job 执行 Fork test suite（现有四条 just test 命令）。
# 日常直接 git push origin main 应被拒绝。
# 发布同步：临时 PR 全绿后才按 README 短暂停用 ruleset并 force-with-lease。
```

禁用脚本跑完后：

```text
gh workflow list --all --repo WAcry/codex
```

只有 `fork-ci.yml`、`fork-release.yml` 和 `fork-sync-upstream.yml` 为 active。

## Upstream

合入策略说明：`.github/workflows/README.md`。闸门：`blocking-ci.yml`。本 fork 不把它标成 required。

## 后果

PR 反馈更快，测试失败在合并后的 `main` 上发现，再提交修复。测试范围保持现有 fork 集合，Windows 保留 release 编译检查；完整 workspace、Bazel 和完整平台矩阵仍由上游验证。`origin/upstream` 会继续看到未发布代码，`origin/main` 则保持“上游 release commit + fork commits”的线性历史。每次更换发布基线都会重写 `main`；已有 fork release tag 不移动，本地长期分支要自行 rebase。
