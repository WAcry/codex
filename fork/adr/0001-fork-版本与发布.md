# 0001. Fork 版本号与 GitHub 发布

- **日期：** 2026-08-31
- **Fork-ADR：** 0001

## Context

上游在开发中的 `main` 上把 `codex-rs/Cargo.toml` 的 `[workspace.package] version` 钉在 `0.0.0`。发版提交把它改成真实版本并打 `rust-vX.Y.Z` 标签；alpha / beta 也有正式的 GitHub prerelease。标签还会触发 `rust-release.yml`：自托管 runner、macOS 签名公证、Azure Windows 签名、R2、npm `@openai/codex`、WinGet。

[WAcry/codex](https://github.com/WAcry/codex) 没有这些 runner、environment 和 secrets。原样打 `rust-v*` 会空等或整条失败。我们需要完整的 Windows / Linux 包，也需要明确每个 fork 版本究竟对应哪次上游发布。

## Decision

版本号：`{上游完整版本}.wa.{N}`。

例子：上游 `0.152.0-alpha.6` 的第一次 fork 发布是 `0.152.0-alpha.6.wa.1`；上游稳定版 `0.152.0` 是 `0.152.0-wa.1`。同一上游版本再发一包，把最后的 `N` 加一。换到更新的上游版本后，`N` 从 `1` 再起。

Git 标签：`wa-v` 加上上面的版本，例如 `wa-v0.152.0-alpha.6.wa.1`。不要用上游的 `rust-v*` 前缀。

`main` 的上游基线只取已经发布的 `rust-v*` 标签，包括 alpha / beta。`codex-rs/Cargo.toml` 保留该上游标签里的真实版本，不跟随 `upstream/main` 的 `0.0.0`。

发布 job 从 `wa-v*` 标签解析出上游版本和 fork 版本。`fork/scripts/stamp-workspace-version.py` 要求 checkout 中的 workspace 版本等于上游版本，再只在本次 checkout 里改成 fork 版本。随后调用仓库已有的 `scripts/build_codex_package.py` 构建标准包。改动不提交。

发布触发：在已合进 `main` 的提交上打 annotated tag，推到 `origin`。`.github/workflows/fork-release.yml` 监听 `wa-v*`。workflow 只解析构建需要的版本格式，不替维护者复核分支和标签操作。

`N >= 1`，版本格式与上游的 stable / alpha / beta 标签一致。输错格式时 workflow 立即失败。

产物（第一期）：

- `codex-package-x86_64-pc-windows-msvc.zip`
- `codex-package-x86_64-unknown-linux-gnu.tar.gz`
- `SHA256SUMS`
- 发布说明里写 fork 提交 SHA、上游发布标签和该标签指向的 commit SHA

包内包含 `codex`、`codex-code-mode-host`、`rg`，以及平台需要的 sandbox / shell 资源。Linux 用 GNU 动态链接，在 `ubuntu-22.04` 上构建，以 glibc 2.35 为最低基线。Windows 用 GitHub-hosted `windows-latest`。二进制不签名。不发 npm、R2、WinGet，不更新 `latest-alpha-cli`。

基于上游 alpha / beta 的版本创建 GitHub prerelease，不能标为 latest；基于上游稳定版的 `.wa.N` 创建普通 Release 并标为 latest。

上游 `.github/workflows/rust-release*.yml` 等文件原样保留。在 GitHub 上禁用，见 ADR 0002。

## Coupling

标签格式和 `fork-release.yml` 里的校验必须一致。上游若改 `scripts/build_codex_package.py`、包布局、二进制名称或 rusty_v8 预编译件，发布 job 会编不过。

未走 fork 发布流程的源码构建会显示上游基线版本。GitHub Release 包显示完整的 `.wa.N` 版本。

上游 Release commit 的 `Cargo.toml` 是真实版本，但 `Cargo.lock` 和 TUI snapshots 仍按 `0.0.0` 维护。`fork-ci.yml` 只在临时 checkout 中把 workspace 版本恢复为 `0.0.0` 再跑上游测试；`main` 不改。

## Reapply

若 `fork-release.yml` 在同步时被删：从本 ADR 和当前 overlay 把文件加回来。不要去改 `rust-release.yml` 来“修”上游发版。

标签解析坏了：先改 workflow 里的正则，再同步本 ADR。版本盖章失败时先确认 `main` 是否仍以对应上游 release tag 为基线。

## 如何确认

```text
# 标签必须被拒绝（缺 .wa.N）
# 合法标签推到 origin 后，Actions 里 fork-release 成功，
# Release 上有 Windows ZIP、Linux tar.gz、SHA256SUMS。
# 解压后：bin/codex[.exe] --version 等于标签去掉 wa-v 前缀。
# 包内有 code-mode host、rg 和该平台的 sandbox 资源。
```

## Upstream

上游发版入口：`.github/workflows/rust-release.yml`。标签约定见该文件顶部注释。workspace 版本：`codex-rs/Cargo.toml` 的 `[workspace.package]`。分支策略见 ADR 0002。

## 后果

用户从 GitHub Releases 装 fork 构建，不能走官方 `npm i -g @openai/codex` 或 `releases.openai.com` 安装脚本来拿我们的改动。macOS 和 ARM 第一期没有包。GNU Linux 包要求 glibc 2.35 或更新版本。每次发版要人工选上游版本号并推 tag；发布有误就增加 `.wa.N`，不要移动已有的发布标签。`main` 不会提前带入尚未发布的上游改动。
