# 0002. main 分支保护与 Fork CI

- **Status：** Accepted
- **日期：** 2026-08-31
- **Fork-ADR：** 0002

## Context

上游合入闸门是 `.github/workflows/blocking-ci.yml` 的 `CI required`，下面挂 Bazel、自托管 Windows、BuildBuddy、`macos-15-xlarge`。仓库名同样是 `codex` 时，表达式 `github.event.repository.name-runners` 会去找并不存在的 `codex-runners`，检查会一直排队。`v8-canary.yml` 在 PR 上也会自己跑。

[WAcry/codex](https://github.com/WAcry/codex) 调查时：main 无 branch protection / ruleset；三种 merge 都开着；Actions 总开关是开的，但 workflow 列表为空；没有自托管 runner。

我们要在 GitHub 上编、测、发，同时不改那 20 多份上游 YAML（改了每次同步都冲突）。个人仓库也必须走 PR，所有者不能绕过。

## Decision

### 工作流文件

新增两份，只服务本 fork：

- `.github/workflows/fork-ci.yml`：PR 和 `main` 的门禁
- `.github/workflows/fork-release.yml`：见 ADR 0001

两份都加 `if: github.repository == 'WAcry/codex'`，避免再 fork 出去时误跑。

不修改上游任何 `.github/workflows/*.yml`。它们进到 Actions 列表之后，用 `fork/scripts/disable-upstream-workflows.ps1` 全部禁用，只留上面两份。`v8-canary`、`rust-release`、`blocking-ci`、`postmerge-ci` 都在禁用名单里。

### PR 门禁（balanced）

GitHub-hosted only。

- Linux `ubuntu-24.04`：`cargo fmt --check`（与上游 rust-ci 相同的 `imports_granularity=Item`）、`cargo clippy --bin codex`、`cargo check --release --bin codex`，再用 `just test` 跑 `codex-core` 的 lib 测试及 `codex-cli`、`codex-tui` 的 crate 测试
- Windows `windows-latest`：`cargo check --release --bin codex`

两边都走 `.github/actions/setup-ci` 和对应 target 的 `setup-rusty-v8`。聚合 job 名称固定为 `Fork CI`，这是 ruleset 里唯一的 required check。

release check 不能删：`tui/src/updates.rs` 等模块在 debug 构建中根本不编译。不做 Bazel、不做 `rust-ci-full`、不把 `sdk.yml` 当 required。

### 合并规则

`main` 只能通过 PR 更新。允许的合并方式只有 squash。合并后删头部分支。禁止 force push 和删除 `main`。要求分支相对 `main` 是最新。required 检查：`Fork CI`。`bypass_actors` 为空，仓库所有者也要过 PR 和 CI。

PR 批准人数为 0，一个人也可以在 CI 绿了之后 squash。CODEOWNERS 不当作强制评审（上游 team 在本 fork 不存在）。

main 只保留这里明确写出的 PR 和 `Fork CI` 门禁。不要再叠加审批人数、标签保护、环境保护或重复检查。默认维护者遵守发布和同步约定。

上游同步：从 `sync/...` 分支开 PR 进 `main`，不要在本地直接推 `main`。同步 PR 同样要过 `Fork CI`，并按 `fork/README.md` 核 overlay 和原则。

功能改动：独立分支，commit 带 `Fork-ADR: NNNN`，squash 进 `main`。

### GitHub 仓库开关

- `allow_squash_merge=true`
- `allow_merge_commit=false`
- `allow_rebase_merge=false`
- `delete_branch_on_merge=true`

用 repository ruleset 实现分支保护，不要用已废弃的 classic branch protection（当前 main 上也没有 classic 规则）。

## Coupling

上游改 `setup-ci`、`setup-rusty-v8`、`codex-rs` 的 fmt 配置、或把 `codex` 二进制挪出 `codex-cli`，fork-ci 会红。禁用名单依赖 workflow 的文件名；上游新增 yml 时要再跑一次 disable 脚本。

Ruleset 写死检查名 `Fork CI`。改 job 的 `name:` 会让 main 合不进去，直到 ruleset 一起改。

## Reapply

`fork-ci.yml` 被同步冲掉：按本 ADR 加回文件，确认聚合 job 仍叫 `Fork CI`。

上游新加了会自动跑的 workflow：跑 `fork/scripts/disable-upstream-workflows.ps1`。不要在上游 yml 里加 `if: github.repository == 'openai/codex'` 来“顺手修”，那是大面积补丁。

Ruleset 被删：用 GitHub API 按 Decision 重建，`bypass_actors` 保持空。

## 如何确认

```text
gh api repos/WAcry/codex --jq "{allow_squash_merge,allow_merge_commit,allow_rebase_merge,delete_branch_on_merge}"
# 期望：squash true，另外两个 merge false，delete_branch_on_merge true

gh api repos/WAcry/codex/rulesets
# main ruleset：required check 为 Fork CI，bypass 为空

# 开一个改 fork/ 文档的 PR：应出现 Fork CI，绿了才能 squash 进 main。
# 直接 git push origin main 应被拒绝。
```

禁用脚本跑完后：

```text
gh workflow list --all --repo WAcry/codex
```

只有 `fork-ci.yml` 和 `fork-release.yml` 为 active。

## Upstream

合入策略说明：`.github/workflows/README.md`。闸门：`blocking-ci.yml`。本 fork 不把它标成 required。

## 后果

门禁比上游窄：Windows 只做 release 编译检查，Linux 只测三个高关联 crate，仍不跑全 workspace、Bazel 和完整平台矩阵。能进 main 的代码仍可能在上游完整矩阵上失败。省下来的是可在 GitHub-hosted 上跑完、以及几乎不改上游 workflow 文件。所有者不能再直接推 `main`，紧急修复也要过 PR。
